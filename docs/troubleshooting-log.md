# Troubleshooting Log

## 시나리오 1 - git commit --amend

### 참여자
- Kim

### 상황
가장 최근에 작성한 로컬 커밋의 메시지를 수정해야 하는 상황을 실습했다.

### 사용한 명령
```bash
git commit --amend
```

### 결과
새로운 커밋을 추가하지 않고 가장 최근 커밋의 내용을 수정했다.

### 왜 이 방법을 선택했는가(Why)
가장 최근의 로컬 커밋만 수정하면 되는 상황이었기 때문에 `git commit --amend`를 사용했다.

### 주의점
amend를 사용하면 기존 커밋의 해시가 변경된다.

이미 공유된 커밋에서는 팀 합의 없이 사용하지 않는다.

## 시나리오 2 - git reset --soft HEAD~1

### 참여자
- Kang

### 상황
최근 로컬 커밋을 취소하면서 작성한 변경 내용은 그대로 유지해야 하는 상황을 실습했다.

### 사용한 명령
```bash
git reset --soft HEAD~1
```

### 결과
최근 커밋은 취소되었지만 변경된 내용은 staging 영역에 그대로 유지되었다.

### 왜 이 방법을 선택했는가(Why)
코드 변경을 삭제하는 것이 아니라 커밋만 다시 작성해야 했기 때문에 `--soft` 옵션을 사용했다.

### 주의점
이미 원격 저장소에 공유된 커밋에는 reset을 사용하지 않는다.

공유된 커밋을 안전하게 취소해야 하는 경우 `git revert`를 사용한다.

---

## 시나리오 3 - git revert

### 참여자
- Joo

### 상황
원격 저장소에 이미 push된 커밋을 Git 히스토리에서 삭제하지 않고 안전하게 취소하는 상황을 실습했다.

실습용 파일 `docs/revert-practice.md`를 커밋하고 원격 저장소에 push한 뒤 해당 커밋을 `git revert`로 취소했다.

### 사용한 명령
```bash
git revert <Joo의 실제 원본 커밋 해시> --no-edit
```

### 결과
기존 커밋은 Git 히스토리에 유지되고 기존 변경 사항을 반대로 적용하는 새로운 Revert 커밋이 생성되었다.

- 원본 커밋: `<Joo의 실제 원본 커밋 해시>`
- Revert 커밋: `<Joo의 실제 Revert 커밋 해시>`

### 왜 이 방법을 선택했는가(Why)
이미 원격 저장소에 공유된 커밋이므로 reset으로 히스토리를 변경하지 않고 새로운 취소 커밋을 생성하는 `git revert`를 사용했다.

### 주의점
`git revert`는 기존 커밋을 삭제하지 않는다.

공유된 커밋을 취소할 때는 reset이나 강제 push 대신 revert를 사용한다.

## 시나리오 4 - git stash / git stash pop

### 참여자
- Kwon

### 상황
현재 브랜치에서 아직 커밋하지 않은 변경 사항이 있는 상태에서 다른 브랜치로 이동해야 하는 상황을 실습했다.

### 사용한 명령
```bash
git stash
git switch <다른-브랜치>
git switch <기존-브랜치>
git stash pop
```

### 결과
커밋하지 않은 변경 사항을 임시 공간에 보관한 뒤 다른 브랜치로 이동할 수 있었다.

기존 브랜치로 돌아온 후 `git stash pop`으로 보관했던 변경 사항을 복원했다.

### 왜 이 방법을 선택했는가(Why)
완성되지 않은 작업을 의미 없는 임시 커밋으로 만들지 않고 잠시 보관하면서 다른 브랜치로 이동하기 위해 stash를 사용했다.

### 주의점
`git stash pop`을 실행할 때 현재 브랜치의 변경 내용과 stash에 저장된 내용이 같은 영역을 수정했다면 충돌이 발생할 수 있다.
